# 기사 JSON 스펙 정의서

> **문서 상태**: v1.0
> **작성일**: 2026-02-26
> **목적**: `kfn-app/src/data/articles/` 에 저장되는 기사 JSON 파일의 구조, 필드 규칙, 작성 가이드 정의

---

## 0. 파일 위치 및 네이밍

```
kfn-app/src/data/articles/opinion-{선수명KR}-{publishedAt Unix ms}.json
```

**예시**
```
opinion-오현규-1771934400000.json
opinion-손흥민-1771470000000.json
```

**규칙**
- 선수명은 한국어 풀네임
- Unix 타임스탬프는 `new Date(publishedAt).getTime()` 값
- 파이프라인 자동 생성 시에도 동일 규칙 적용

## 1. 최상위 구조

```json
{
  "id": "string",
  "title": "string",
  "subtitle": "string",
  "summary": "string",
  "content": "string (Markdown)",
  "playerName": "string (영문)",
  "playerNameKr": "string (한국어)",
  "team": "string",
  "league": "string",
  "matchInfo": "string",
  "publishedAt": "string (ISO 8601)",
  "thumbnailUrl": "string",
  "tags": ["string"],
  "evidence": { ... }
}
```

> `adCurations`는 기사 JSON에 포함하지 않음. `src/data/adCurations.ts`에서 `playerNameKr` 기준으로 자동 조회.

### 필드 정의

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `id` | string | ✅ | 고유 식별자. 파일명과 동일한 규칙 (`opinion-{선수명KR}-{Unix ms}`) |
| `title` | string | ✅ | 기사 제목. 핵심 지표 + 임팩트 요약 형식 |
| `subtitle` | string | ✅ | 리그/경기 정보 한 줄 요약 |
| `summary` | string | ✅ | 2~3문장 기사 요약. 리스트 뷰에 표시됨 |
| `content` | string | ✅ | 본문 (Markdown). 아래 [content 작성 규칙](#4-content-markdown-구조) 참고 |
| `playerName` | string | ✅ | 선수 영문명 (예: `"Hyeon-Gyu Oh"`) |
| `playerNameKr` | string | ✅ | 선수 한국어명 (예: `"오현규"`). **로더 유효성 검사 필수 필드** |
| `team` | string | ✅ | 소속 팀명 (영문) |
| `league` | string | ✅ | 리그명 (영문) |
| `matchInfo` | string | ✅ | 경기 정보 한 줄 (예: `"쉬페르리그 25/26 \| 베식타스 4-0 괴즈테페"`) |
| `publishedAt` | string | ✅ | ISO 8601 형식 (예: `"2026-02-24T12:00:00Z"`) |
| `thumbnailUrl` | string | ✅ | 썸네일 이미지 URL. 없으면 빈 문자열 `""` |
| `tags` | string[] | ✅ | 선수명·팀명·리그명·핵심키워드 (최대 5개 권장) |
| `evidence` | object | ✅ | 차트·데이터 근거. 아래 [evidence 구조](#2-evidence-구조) 참고 |

## 2. evidence 구조

```json
"evidence": {
  "charts": [ ... ],
  "dataRows": [ ... ],
  "sources": [ ... ]
}
```

### 2-1. charts

차트는 **2~4개** 권장. 지원 타입: `bar` / `radar` / `pie` / `line`

```json
{
  "id": "unique-chart-id",
  "title": "차트 제목",
  "type": "bar | radar | pie | line",
  "data": [ ... ],
  "dataKeys": ["string"],
  "colors": ["#hex"]
}
```

#### bar 차트 data 형식
비교 대상이 있는 수치 지표에 사용.
```json
{ "name": "항목명", "선수명": 숫자, "리그평균": 숫자 }
```

#### radar 차트 data 형식
종합 퍼포먼스 다각형 시각화에 사용.
```json
{ "stat": "항목명", "value": 숫자(0~100) }
```

#### pie 차트 data 형식
감성 분석 등 비율 시각화에 사용. `fill` 필드로 색상 개별 지정.
```json
{ "name": "항목명", "value": 숫자, "fill": "#hex" }
```

#### line 차트 data 형식
시계열 추이 시각화에 사용.
```json
{ "match": "레이블", "지표명": 숫자 }
```

#### 권장 차트 구성 (기본 4개)

| 순서 | 차트 타입 | 내용 |
|------|-----------|------|
| 1 | bar | 이번 경기 주요 지표 (선수 vs 리그/팀 평균) |
| 2 | radar | 종합 퍼포먼스 (6개 항목, 0~100 스케일) |
| 3 | pie | 현지 여론 감성 분석 (긍정/중립/부정) |
| 4 | line | 시즌 누적 추이 또는 연속 기록 |

---

### 2-2. dataRows

근거 데이터 테이블. **3~5개** 권장.

```json
{
  "label": "지표명",
  "value": "핵심 수치 또는 팩트",
  "interpretation": "이 수치가 왜 의미 있는지 2~3문장 설명",
  "source": "출처명",
  "sourceUrl": "https://..." 
}
```

| 필드 | 설명 |
|------|------|
| `label` | 짧은 지표명 (예: `"경기 평점"`, `"Reddit 반응"`) |
| `value` | 핵심 값 (예: `"9.6 / 10.0"`, `"181 추천"`) |
| `interpretation` | AI 해석 텍스트. 숫자의 맥락/의미 설명 |
| `source` | 출처 표시명 (예: `"FotMob"`, `"Reddit r/MLS"`) |
| `sourceUrl` | 실제 URL. 없으면 `""` |

---

### 2-3. sources

기사 작성에 사용된 전체 출처 목록.

```json
{
  "url": "https://...",
  "title": "출처 기사/스레드 제목",
  "type": "news | reddit | stats"
}
```

| `type` 값 | 용도 |
|-----------|------|
| `news` | 현지 언론 기사 |
| `reddit` | Reddit 스레드/댓글 |
| `stats` | 통계 사이트 (FotMob, Sofascore 등) |

## 3. 유의미한 시각자료 제작 지침

> **참고 출처**: Edward Tufte *The Visual Display of Quantitative Information* (1983), StatsBomb Analytics Blog, The Athletic Data Journalism, CAP Data Visualization Standards, Observable HQ Radar Chart Research, UNHCR Dataviz Platform

---

### 3-1. 핵심 원칙

#### 데이터가 말하게 하라 (Tufte)
- **Data-Ink Ratio 최대화**: 차트에 표시되는 모든 요소가 데이터를 전달해야 함. 장식적 요소(배경 그라데이션, 불필요한 테두리, 3D 효과)는 모두 제거
- **Chartjunk 금지**: 데이터 해석에 기여하지 않는 시각 요소는 노이즈다. 격자선은 최소화, 레이블은 직접 표기 권장
- **Lie Factor = 1 유지**: 시각적 크기 변화가 실제 데이터 변화 비율과 일치해야 함. 축을 0에서 시작하지 않으면 차이가 과장됨

#### 비교 기준을 반드시 제시하라 (StatsBomb / The Athletic)
- **단독 수치는 무의미**: "오현규 3골"이 아니라 "리그 평균 0.8골 대비 오현규 3골"이어야 맥락이 생긴다
- **비교 기준 우선순위**: ① 리그 전체 평균 → ② 동일 포지션 평균 → ③ 팀 내 평균 → ④ 선수 자신의 직전 시즌
- **백분위 표기 병행**: StatsBomb 레이더 방식처럼 원시값과 함께 "리그 상위 N%" 표기 시 훨씬 강력한 맥락 제공

#### 하나의 차트, 하나의 메시지
- 차트 제목이 결론 문장이 되어야 함 (예: `"최근 3경기 공격 기여"` → `"3경기 연속 리그 평균 3배 초과"`)
- 한 차트에서 두 개 이상의 주장을 하면 독자 인지 부하가 증가함

---

### 3-2. 차트 타입 선택 기준

```
무엇을 보여주려 하는가?
│
├─ 선수 vs 평균/팀원 비교      → bar
├─ 선수의 다차원 프로필        → radar (단, 아래 제약 준수)
├─ 여론 비율 (긍정/중립/부정)  → pie (단, 세그먼트 ≤ 4개)
├─ 시간에 따른 추이/누적       → line
│
└─ 위 어디에도 해당 없음       → chart 생략, dataRow로 대체
```

**차트를 만들지 말아야 할 때**
- 데이터 포인트가 2개 이하인 경우 (line 차트)
- 비교 기준(리그 평균 등)을 구할 수 없는 경우 (bar 차트)
- 값 차이가 시각적으로 구별 불가능한 경우 (예: 51% vs 49% pie)
- 데이터가 단순한 팩트 하나인 경우 → `dataRow`로 충분

---

### 3-3. bar 차트 세부 지침

**사용 조건**: 카테고리 간 크기 비교, 선수 vs 기준값 비교

| 규칙 | 내용 |
|------|------|
| 축 시작점 | **반드시 0에서 시작**. 잘린 축은 차이를 과장함 (Tufte Lie Factor) |
| 항목 수 | **3~6개** 권장. 7개 이상이면 가독성 저하 |
| 비교 기준 | `리그평균`, `팀평균`, `포지션평균` 중 하나 반드시 포함 |
| 정렬 | 가능하면 값 내림차순 정렬 (비교 패턴 인식 용이) |
| 색상 | 선수 데이터: `#d90828` (kfn-red), 비교 기준: `#94a3b8` (회색) |

**좋은 예**
```json
{ "name": "찬스 창출", "손흥민": 5, "MLS평균": 1.4 }
```
→ 5배 차이가 시각적으로 명확

**나쁜 예**
```json
{ "name": "패스 성공률", "선수": 79, "평균": 75 }
```
→ 4%p 차이는 bar 차트로 강조할 가치 없음. `dataRow`로 서술 처리

---

### 3-4. radar 차트 세부 지침

**사용 조건**: 선수의 다차원 종합 프로필. 단일 경기보다 시즌 누적 비교에 적합

> **주의**: radar 차트는 축 순서에 따라 시각적 형태가 완전히 달라진다 (Observable HQ 연구). 항목 배치가 곧 해석이다.

| 규칙 | 내용 |
|------|------|
| 축 개수 | **5~7개** 고정. 4개 이하는 bar, 8개 이상은 두 차트로 분리 |
| 값 스케일 | **반드시 0~100 백분위 정규화**. 원시값 혼용 금지 (StatsBomb 방식) |
| 축 배치 | 공격 지표 → 기술 지표 → 체력/수비 지표 순서로 시계방향 배치 |
| 항목 선택 | 포지션 특성과 기사 내러티브에 직접 관련된 항목만 포함 |
| 시리즈 수 | **단일 시리즈만** 사용. 2개 이상 겹치면 폴리곤이 뒤섞여 해독 불가 |

**포지션별 권장 축 구성**

| 포지션 | 권장 항목 |
|--------|----------|
| 공격수 | 골 결정력 · 슈팅 파워 · 드리블 · 오프더볼 · 패스 · 압박 기여 |
| 미드필더 | 패스 성공률 · 키패스 · 볼 키핑 · 드리블 · 수비 기여 · 활동량 |
| 수비수 | 공중볼 · 태클 · 차단 · 빌드업 패스 · 위치 선정 · 압박 성공 |

---

### 3-5. pie 차트 세부 지침

**사용 조건**: 전체 대비 비율. KFN에서는 **여론 감성 분석 전용**으로 사용

> **주의**: 인간은 각도와 면적을 부정확하게 인식한다. pie는 정밀 비교가 아닌 '대략적 구성 확인'에만 유효 (Atlassian Data Charts Research)

| 규칙 | 내용 |
|------|------|
| 세그먼트 수 | **최대 4개**. 3개(긍정/중립/부정)가 최적 |
| 최소 비율 | 5% 미만 세그먼트는 "기타"로 묶거나 삭제 |
| 값 유사성 | 세그먼트 간 차이가 10%p 미만이면 pie 비적합 → bar로 대체 |
| 색상 의미 | 긍정 `#22c55e`, 중립 `#94a3b8`, 부정 `#ef4444` 고정 |
| 합계 | 모든 `value`의 합이 반드시 **100** |

**감성 분석 산출 기준** (데이터 수집 시 통일)
- 분석 대상: 해당 경기 Reddit 스레드 상위 댓글 100개
- 긍정: 선수/팀에 명확한 칭찬·지지 댓글
- 중립: 사실 서술, 질문, 판단 유보 댓글
- 부정: 비판·실망·조롱 댓글

---

### 3-6. line 차트 세부 지침

**사용 조건**: 시간에 따른 추이, 누적 기록, 연속 기록 변화

| 규칙 | 내용 |
|------|------|
| 최소 데이터 포인트 | **4개 이상**. 3개 이하면 추세를 말할 수 없음 |
| x축 간격 | 경기 단위로 균등하게. 날짜보다 경기 번호(라운드) 권장 |
| y축 | 0 시작이 원칙이나, 변화의 미세한 패턴이 핵심이면 범위 조정 가능 (단, 제목에 명시) |
| 데이터 스무딩 | The Athletic 방식처럼 노이즈가 많은 데이터(경기 평점 등)는 이동평균 적용 고려 |
| 시리즈 수 | **1~2개**. 3개 이상은 서로 다른 차트로 분리 |

**추천 활용 시나리오**
- 시즌 내 공격포인트 누적 (선형 증가 패턴 확인)
- 최근 N경기 평점 추이 (폼 흐름 파악)
- 출전 시간 변화 (팀 내 입지 변화 시각화)

---

### 3-7. 전체 차트 세트 구성 원칙

**4개 차트 구성 시 권장 순서와 목적**

| 순서 | 차트 | 핵심 질문 | 비고 |
|------|------|-----------|------|
| 1 | bar | "이 경기에서 얼마나 뛰어났나?" | 리그 평균과 직접 비교 |
| 2 | radar | "이 선수는 어떤 유형의 선수인가?" | 시즌 누적 기반 정규화값 |
| 3 | pie | "현지 반응은 어떤 분위기인가?" | 감성 분석 전용 |
| 4 | line | "이 활약이 일회성인가, 흐름인가?" | 최근 5경기 이상 추이 |

**차트 2개만 만들어야 한다면**: bar(1번) + pie(3번)  
**차트 3개만 만들어야 한다면**: bar(1번) + pie(3번) + line(4번)  
radar는 데이터가 정규화되지 않으면 생략

| 용도 | 색상 | 비고 |
|------|------|------|

**색맹 접근성**: 색상만으로 의미를 구분하지 않도록 bar 차트에서 레이블 병기 권장 (Smashing Magazine Accessibility Standards 2024)

## 4. content Markdown 구조

`content` 필드는 JSON 문자열 안에 `\n`으로 줄바꿈하는 Markdown.

```markdown
## 경기 요약

[경기 결과 및 선수 활약 2~3문단]

## 해외 현지 반응 (AI 요약)

### Reddit r/{서브레딧} 반응
- **최다 추천 (N)**: "인용구"
- **주요 반응 1**: "인용구" (N 추천)
- **주요 반응 2**: "인용구" (N 추천)

### {현지 매체명} 반응
- **{매체}**: "인용구"
```

## 6. 파이프라인 출력 포맷 (래퍼 포맷)

AI 파이프라인(n8n)이 자동 생성하는 경우 아래 래퍼 포맷으로 출력됨. `articleLoader.ts`가 자동으로 `article` 키를 추출.

```json
[
  {
    "article": { ... },
    "meta": {
      "id": "opinion-{선수명KR}-{Unix ms}",
      "playerNameKr": "선수명",
      "qaPass": true,
      "qaAttempt": 1,
      "publishedAt": "ISO 8601"
    }
  }
]
```

**수동 작성 시**에는 래퍼 없이 article 객체를 직접 저장해도 됨.

## 7. 로더 유효성 검사 조건

`kfn-app/src/utils/articleLoader.ts`의 `isValidArticle()` 기준:

```
id        → typeof string
title     → typeof string
content   → typeof string
playerNameKr → typeof string
```

위 4개 필드가 모두 string이 아니면 로드 대상에서 제외됨.
